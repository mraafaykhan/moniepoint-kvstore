Technical Details
Under the hood of the KVStore engine
LSM-Tree (Log-Structured Merge Tree) architecture:

Write path:
  1. Append to WAL (write-ahead log) for durability
  2. Insert into Memtable (in-memory skip list)
  3. When Memtable is full → flush to SSTable on disk

Read path:
  1. Check Memtable first (most recent data)
  2. Check Bloom filters on SSTables (avoid unnecessary I/O)
  3. Binary search within SSTable blocks

This design optimizes for write throughput while maintaining efficient reads through Bloom filters and sorted structure.
Block-based SSTable format:

SSTable Layout:
  [Data Block 0][Data Block 1]...[Data Block N]
  [Meta Block (Bloom Filter)]
  [Index Block]
  [Footer: offsets + magic number]

Each Data Block:
  [Entry][Entry]...[CRC32 checksum]

Each Entry:
  [key_len: 4B][val_len: 4B][key][value][tombstone: 1B]

CRC32 checksums on every block ensure data integrity. Bloom filters provide O(1) key existence checks with ~1% false positive rate.
Leveled compaction (inspired by LevelDB/RocksDB):

Level sizing:
  L0: 4 SSTables (triggers compaction)
  L1: 10 MB total
  L2: 100 MB total (10x growth per level)
  L3: 1 GB total

Compaction process:
  1. Pick SSTable from Ln with key overlap in Ln+1
  2. Merge-sort overlapping SSTables
  3. Remove tombstoned entries at deepest level
  4. Write new SSTables to Ln+1

This bounds read amplification to O(levels) while maintaining good space amplification.
Custom binary TCP protocol:

Frame format:
  [Length: 4 bytes][Command: 1 byte][Payload: N bytes]

Commands:
  0x01 PUT     [key_len][key][value]
  0x02 GET     [key_len][key]
  0x03 DELETE   [key_len][key]
  0x04 BATCH    [count][entries...]
  0x05 RANGE    [start_key][end_key]

Response:
  [Length: 4 bytes][Status: 1 byte][Payload: N bytes]

Connection pooling and keep-alive for efficient reuse.
Raft consensus protocol (3-node cluster):

Two core RPCs:
  1. RequestVote — leader election
  2. AppendEntries — log replication + heartbeat

Election:
  • Randomized timeout: 150-300ms
  • Candidate requests votes from peers
  • Majority wins → becomes leader
  • Typical election: <600ms

Replication:
  • Leader appends to local log
  • Sends AppendEntries to followers
  • Committed once majority acknowledges
  • Followers apply committed entries

Provides linearizable reads and writes with automatic failover.
